# OpenMe 方向与待办全景梳理

**日期**：2026-05-15  
**阶段**：自用验证 → 准备外部用户  
**北极星指标**：WAO（Weekly Adopted Outputs）≥ 3 件/周

---

## 优先级说明

- 🔴 **P0 — 立即做**：当前阶段的核心假设验证，或阻塞后续工作的前置条件
- 🟡 **P1 — 本月内**：产品价值提升明确，技术路径清晰
- 🟢 **P2 — 下阶段**：方向正确但不紧迫，等 P0/P1 稳定后再做
- 🔵 **P3 — 远期**：有价值但成本高，规模化后再考虑

|--------|------|---------|---------|
| 🔴 P0 | 生成 10 篇内容草稿，统计实际发布率 | ≥5 篇无需大改可发布（WAO 核心假设） | 1 天 |
| 🔴 P0 | 飞书文档写入 demo | API 跑通，无权限障碍 | 2 小时 |
| 🔴 P0 | 即刻/少楠社群发一条，测定位共鸣 | 获得 10+ 真实互动 | 30 分钟 |
| 🟡 P1 | 5 个目标用户付费意愿访谈 | ≥3 人愿意付 ¥99+/月 | 1 周 |
| 🟡 P1 | 3 个非技术用户独立冷启动测试 | ≥2 人能独立完成（冷启动是 Launch Blocker） | 1 周 |
| 🟢 P2 | PIPL 合规研究 | 找到明确合规路径或调整架构 | 3 天 |

## 框架二：人格系统升级（Persona Layer）
> 来源：openme-reference-projects.md（Hermes Agent）/ improve-codebase-architecture 分析  
> **技术架构改动的起点，影响 bot 回答质量和可维护性。**

### 目标：memories.json → 四文件系统

| 优先级 | Task | 说明 |
|--------|------|------|
| 🔴 P0 | 创建 `persona.py` 模块 | 统一管理四文件，暴露 `build_system()` 和 `append(section, content)` 接口，`self_feishu.py` 不再直接碰文件 |
| 🔴 P0 | 从头写 `SOUL.md` | 核心人格：语气、风格、行为约束、三种子模式（推演/镜子/记忆）。几乎不变，精雕细琢 |
| 🔴 P0 | 从头写 `USER.md` | 当前状态：职业、正在做的事、短期目标、当前关注的问题。变化最频繁，保持精简（参考 Hermes ~1,375 字符上限） |
| 🔴 P0 | 从头写 `MEMORY.md` | 跨 session 积累的关键事实：经历、观点、判断、偏好。从旧 memories.json 精选迁移（参考 Hermes ~2,200 字符上限） |
| 🔴 P0 | 手动写 `SKILLS.md` | Bot 当前已有能力说明书：推演框架、记忆检索逻辑、/remember 使用、内容生成（未来） |
| 🔴 P0 | 旧 `memories.json` 存档 | 重命名为 `memories_archive.json`，不删除 |
| 🟡 P1 | `/remember` 升级支持指定写入 section | 例如 `/remember soul 不要用"您"这种敬语`，当前只能写入补充 |
| 🟢 P2 | Persona drift detection（SoulClaw 方案） | 检测 bot 回答是否随时间偏离 SOUL.md 定义，防止人格漂移 |

## 框架三：记忆层升级（Memory Layer）
> 来源：openme-reference-projects.md（Second Me HMM / obsidian-second-brain / second-brain-ai-assistant-course）

### 当前状态：L0 ✅，L1 ❌，L2 部分实现

| 优先级 | Task | 说明 |
|--------|------|------|
| 🟡 P1 | RAG 触发语义化 | 当前 9 个关键词硬触发，改为语义相似度阈值判断，或改为每次都检索再由调用方决定是否注入 |
| 🟡 P1 | n_results 5 → 10 | 当前召回数量偏少，扩大至 10 条，观察回答质量变化 |
| 🟡 P1 | 入库质量过滤 | 入库前用 LLM 对每个 chunk 打分（0-10），低于阈值不入库，过滤闲聊/重复/低信息密度内容 |
| 🟢 P2 | L1 摘要层脚本 | 定期对 ChromaDB 内容按主题聚类，LLM 生成段落级摘要（"关于职场关系的模式""关于决策风格的模式"），存入独立 collection |
| 🟢 P2 | 重写而非追加 | 新内容入库时检测是否与已有内容矛盾，自动更新旧记忆而不是堆叠 |
| 🟢 P2 | 双时态事实追踪 | 记录"在某时间点相信 X，后来转向 Z"，让记忆反映成长轨迹而不是静态快照 |
| 🟢 P2 | 关联发现脚本（Connector agent） | 对向量库跨来源做关联分析，找出工作/社交/笔记中指向同一主题的片段，显式存入 L1 层 |
| 🔵 P3 | 智能引用 | Bot 回答时标注来源（来自哪段对话/哪篇笔记），让用户可追溯原始记忆 |

## 框架四：数据输入层扩充（Input Layer）
> 来源：openme-product-design.md / openme-reference-projects.md（Khoj）  
> 输入越多样，积累层越立体，输出质量越高。

| 优先级 | Task | 说明 |
|--------|------|------|
| 🟡 P1 | 腾讯会议记录接入 | 导出文字版纪要 → 解析入库，补充效率层数据源 |
| 🟡 P1 | Fomo 日记接入 | 调研 Fomo 导出格式，写解析脚本；日记是密度最高的自我表达 |
| 🟡 P1 | bot 对话记录定期向量化 | SQLite 历史对话定期批量向量化入库，历史也成为可检索记忆 |
| 🟢 P2 | 飞书消息自动同步 | 重要飞书对话自动流进 ChromaDB，不需要手动导出 |
| 🟢 P2 | 阅读标注接入 | 微信读书导出 / Kindle 标注 → 入库，展示品味和思考框架 |
| 🟢 P2 | 其他平台内容接入 | 即刻发帖、小红书、公众号历史内容 → 入库 |
| 🔵 P3 | 多格式文档解析（Khoj 方案） | 支持 PDF / Notion / Word 直接入库，替换现有手写 ingest 脚本 |
| 🔵 P3 | 朋友圈/收藏内容 | 兴趣图谱建立，需要单独导出工具 |

## 框架五：效率层 — 工作 Agent（Efficiency Layer）
> 来源：openme-product-design.md / self-bot.md 待办 / openme-assumptions-priority.md  
> **验证效率层价值的首个 agent，也是 WAO 的重要贡献来源。**

| 优先级 | Task | 说明 |
|--------|------|------|
| 🔴 P0 | 飞书文档写入 demo | 验证 API 权限和限制，2 小时内可完成，是效率层所有功能的前置 |
| 🟡 P1 | PRD 生成 agent（首个工作 agent） | 接收需求材料，bot 主动识别关键判断点并提问，自动生成 PRD 至飞书文档。成功标准：节省 ≥50% 时间 |
| 🟡 P1 | 会议纪要 agent | 粘贴腾讯会议文字记录，自动生成结构化纪要 + 行动项 |
| 🟢 P2 | 自定义 agent 创建 | 用户描述工作流程，bot 自动生成专属 agent 行为（预设模板 + 自定义扩展） |
| 🟢 P2 | SOP 引擎（zeroclaw 参考） | 把常见工作流编码为固定步骤，减少 LLM 自由发挥，让 agent 行为更可预测 |
| 🟢 P2 | 多维表格同步 | 工作产出自动同步至飞书多维表格，实现结构化管理 |
| 🔵 P3 | MCP 工具接入（nanobot 参考） | 接入飞书日历、搜索工具，让 bot 知道日程并能主动查询 |

## 框架六：输出层 — 内容生成（Output Layer）
> 来源：self-bot.md 待办 / openme-north-star.md / openme-pre-mortem.md  
> **WAO 最核心的贡献来源，也是最高优先级的假设验证对象。**

| 优先级 | Task | 说明 |
|--------|------|------|
| 🔴 P0 | 手动生成 10 篇内容草稿并测试发布率 | 用现有 bot + 手动触发，测试内容质量假设，≥50% 发布率才进入开发 |
| 🟡 P1 | 内容草稿生成脚本 | 基于 ChromaDB 近期内容 + MEMORY.md，自动生成长文/短文草稿 |
| 🟡 P1 | 内容质量过滤 | 生成后自动打分，低于阈值不推给用户，避免劣质内容损害个人品牌 |
| 🟡 P1 | 飞书卡片推送草稿 | 草稿生成后推送飞书卡片（一键发布/修改/跳过），复用已有流式卡片架构 |
| 🟢 P2 | Hub 独立后台进程（OpenHanako 参考） | 独立进程运行定时任务（内容生成、记忆整理、主动触达），不阻塞对话 |
| 🟢 P2 | 用户反馈闭环 | 内容发布后 bot 主动问"效果如何"，将反馈写入记忆，调整下次内容方向 |
| 🟢 P2 | 公众号/小红书发布接入 | 当前用户手动发布，后续接入平台 API 实现一键发布 |
| 🔵 P3 | 内容日历 | 多维表格追踪每周内容计划和实际发布，可视化 WAO 趋势 |

## 框架七：冷启动优化（Cold Start）
> 来源：openme-pre-mortem.md（Launch Blocker）/ openme-product-design.md  
> **面向外部用户的关键门槛，当前冷启动对非技术用户几乎不可能独立完成。**

| 优先级 | Task | 说明 |
|--------|------|------|
| 🟡 P1 | 对话式冷启动引导 | 新用户进来 bot 主动提问（你做什么工作？最近在想什么？），10 分钟内建立初始记忆，无需上传文件 |
| 🟡 P1 | 第一次对话推荐问题 | 冷启动完成后 bot 主动推送 3 个推荐问题，降低"不知道怎么用"的流失 |
| 🟡 P1 | 简化文件上传流程 | 拖入即处理，向量化/入库/索引全部自动完成，用户不感知技术细节 |
| 🟢 P2 | 冷启动进度提示 | 告诉用户"你的记忆库已有 X 条，建议上传 Y 来丰富 Z 方面" |

## 框架八：代码架构优化（Code Architecture）
> 来源：improve-codebase-architecture 分析  
> **技术债偿还，不影响功能但影响可维护性和扩展速度。**

| 优先级 | Task | 说明 |
|--------|------|------|
| 🟡 P1 | `persona.py` 模块提取 | 从 self_feishu.py 分离人格管理逻辑（与框架二同步进行） |
| 🟡 P1 | `embedding.py` 统一 | 合并 ingest.py / ingest_wechat.py / rag.py 三处重复的 embed() + 重试逻辑 |
| 🟡 P1 | `<think>` 过滤统一 | 提取 stream.py，两端共用同一个流式过滤器 |
| 🟢 P2 | `config.py` 集中配置 | 启动时统一读取并校验所有环境变量，缺失即报错 |
| 🟢 P2 | 消息路由重构 | on_message() 拆出 CommandDispatcher，命令处理与对话流程解耦 |
| 🔵 P3 | 渠道适配器（PocketPaw 方案） | 飞书/Web 渠道抽象为适配器，核心 agent 逻辑只写一次，新增渠道只接适配器 |
| 🔵 P3 | token-based 记忆管理（nanobot 方案） | 动态压缩对话历史，在 token 预算内最大保留信息，替换当前"最近 20 条" |

## 执行顺序建议

### 本周（验证优先）
```
Day 1-2: 手动生成 10 篇内容草稿 → 统计发布率（最高优先级假设验证）
Day 3:   飞书文档写入 demo（2小时）
Day 4:   即刻发一条，测定位共鸣（30分钟）
Day 5:   开始写 SOUL.md / USER.md / MEMORY.md / SKILLS.md 四文件
```

### 本月（架构打基础）
```
Week 2: persona.py 模块 + 四文件系统上线
Week 2: embedding.py 统一 + <think> 过滤统一
Week 3: RAG 触发优化 + n_results 扩大
Week 3: 腾讯会议 / Fomo 日记接入
Week 4: PRD 生成 agent 第一版
Week 4: 对话式冷启动引导
```

### 下阶段（产品化准备）
```
内容草稿生成脚本 + 质量过滤 + 飞书卡片推送
Hub 后台进程上线
5个用户付费意愿访谈
L1 摘要层脚本
外部用户冷启动测试
```

## 当前最大风险提示

| 风险 | 来源 | 缓解方向 |
|------|------|---------|
| 内容草稿质量不达标 | pre-mortem Tiger #1 | 本周立即验证，不达标则调整 prompt/数据 |
